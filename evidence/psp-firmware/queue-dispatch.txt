This is a direct hand-décodage of the exact structure the bc250 RE notes
describe, and it reproduces the status codes this repo already measured from
the live SMU (`smu-raw.md`): 0xFE = unknown command, 0xFD = rejected-prereq,
0xFC = rejected-busy. The dispatch is: message id (low 8 bits) -> per-queue
handler table entry (8 bytes: 4-byte pointer at +0, config/guard at +5) ->
guard test -> callx8 the handler.

Why this matters for the Curve Optimizer question: the CO messages 0x55 /
0x54 / 0x64 returning 0xFF (Failed) rather than 0xFE (UnknownCmd) means their
table entries are non-null and the handlers run and then refuse. The table
entry is where "recognised and refused" lives.

Handler tables found by structure (arrays of 8-byte entries whose pointer column
is an Xtensa function prologue, `36 4x 00` / `36 6x 00`):

  @0x13b90  48 entries, default 0x2bd88, distinct handlers at ids
            0x00,0x02,0x06,0x08,0x09,0x0a,0x0b,0x0c,0x0d,0x0e,0x0f,0x18,...
  @0x6f94   18 entries, config dword 0x00000006/0x00000106
  @0x70c4   14 entries
  @0x9884   18 entries -- pointers into the thunk block near 0xf50 (0xf50, 0xf5c,
            0xf68, 0xf74, 0xf80, 0xf98, 0xfb0), i.e. a vector/thunk table, not a
            message table
  @0x6b6c   9 entries, config 0x00000201

What was NOT pinned down: which of these is the MP1 message queue, and the
handler for id 0x55. The map from a live SMU mailbox to a queue index (the
dispatcher's `a2`) is set up in RAM at boot from the image, and the tables that
appear in the image top out around 18-64 entries -- so the id->handler array
for the MP1 queue (which must reach at least 0x55) is either built in RAM at
run time or indexed differently from the 8-byte model above. Resolving it is the
next step, and it wants a real Xtensa disassembler with a RAM map (Ghidra 11.1+
ships Xtensa), not rasm2 by hand.
