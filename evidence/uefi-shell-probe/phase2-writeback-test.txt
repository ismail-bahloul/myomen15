Phase 2 -- the write-back test (TYPE THESE BY HAND, ONE AT A TIME)
====================================================================

Do not save this as a .nsh and run it. Type each line at the `Shell>` (or
`FS1:\>` once you have selected the drive) prompt and read the output
before typing the next one. If anything looks wrong, stop and reboot
without continuing -- Setup has already been backed up in phase 1, and
again in step 1 below.

The question this answers: does the firmware itself refuse a SetVariable
on `Setup`, or does it only fail under Linux because efivarfs marks that
inode immutable? The test writes back the exact bytes already there --
a no-op if it succeeds, the same kind of test firmware-limits.md already
did successfully on the writable `Timeout` variable. This was rehearsed
in a QEMU+OVMF test VM first (see README.md) to confirm the exact
dmpstore syntax and that its error reporting (e.g. "Write Protected") is
clear and does not silently look like success.

0. Make sure you're on the right drive (should already be, from phase 1):

     fs1:

1. Fresh backup, immediately before the test:

     dmpstore Setup -guid EC87D643-EBA4-4BB5-A1E5-3F3E36B20DA9 -s dumps\Setup-preloop.dat

   Confirm it printed "Save variable to file..." and listed the Setup
   variable, not an error.

2. The actual write-back -- this is the one that matters:

     dmpstore Setup -guid EC87D643-EBA4-4BB5-A1E5-3F3E36B20DA9 -l dumps\Setup-preloop.dat

   The name and -guid MUST be repeated here. Confirmed in testing: without
   them, -l silently falls back to filtering on the default
   EFI_GLOBAL_VARIABLE GUID, reports "No matching variables found" for
   that wrong GUID, and never touches Setup at all -- which looks like
   nothing happened, but isn't actually the answer to the question.

   Read the status line carefully. Two possible outcomes:
     - "Load and set variables from file" followed by the Setup entry
       with no error under it -> the firmware accepts the write; the
       Linux-side "immutable" refusal is a Linux/efivarfs policy, not a
       firmware lock.
     - "Failed to set variable Setup: Write Protected" (or Access
       Denied / Security Violation) -> the firmware itself refuses it,
       and Sure Start's protection is real at this layer too, not just
       an efivarfs convention. This exact wording was reproduced in
       testing for genuinely protected variables, so it's an
       unambiguous signal, not a guess.

   Write down or photograph the exact message either way.

3. Re-dump Setup again, to a different filename, and keep both:

     dmpstore Setup -guid EC87D643-EBA4-4BB5-A1E5-3F3E36B20DA9 -s dumps\Setup-postloop.dat

   These two files (Setup-preloop.dat, Setup-postloop.dat) should be
   byte-identical if step 2 was genuinely a no-op. Bring both back --
   the comparison itself is part of the answer, the same way this repo
   already learned not to trust "it looks the same" without checking.

4. Reboot normally. Re-enter the BIOS setup once to visually confirm
   nothing looks different, before trusting the machine with anything
   else.

Stop here regardless of the result and bring back:
  - the exact message from step 2
  - dumps\Setup-preloop.dat and dumps\Setup-postloop.dat

Do not proceed to poking the 9 unnamed offsets (21, 22, 23, 174, 244,
276, 278, 280, 284, 316 -- see efi-nvram.md) in the same session. That is
a separate, one-offset-at-a-time experiment with its own revert plan,
worth planning fresh once the answer above is known.
